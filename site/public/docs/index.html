Introduction

Documentation

Run DumpStation

Everything you need to install, configure and operate DumpStation: a self-hosted server that runs pg_dump on a schedule, stores verified artifacts in S3-compatible storage, and reaches private databases through outbound-only agents.

Quick start →Docker Compose, a generated .env, first sign-in. About five minutes. Configuration →Every environment variable, searchable, with defaults. Agents →Back up databases in private networks without opening a port. Troubleshooting →All error codes and what to do about each.

The pieces

  • Server (ghcr.io/monzim/dumpstation): one Go binary serving the web UI, the REST API (/api/v1) and the agent API (/agent/v1). It schedules jobs, runs direct backups, applies retention and sends notifications.
  • Metadata database: a PostgreSQL instance for DumpStation's own configuration, history and encrypted secrets.
  • Object storage: one or more S3-compatible buckets where artifacts live.
  • Agents (ghcr.io/monzim/dumpstation-agent, optional): small workers next to databases the server can't reach.

Quick start

The production Compose bundle in configs/ runs the server and its metadata database. Direct backups work out of the box.

  1. Get the bundle
    terminal
    git clone https://github.com/monzim/DumpStation.git
cd DumpStation/configs
cp .env.example .env
  2. Fill in the required values

    Generate secrets and set the URL browsers and agents will use:

    .env
    POSTGRES_PASSWORD=   # openssl rand -base64 24
JWT_SECRET=          # openssl rand -base64 64
DUMPSTATION_SECRET_KEY=   # openssl rand -base64 32  (keep it safe!)
PUBLIC_URL=https://backups.example.com
SYSTEM_USERNAME=admin
APP_ENV=production

    Back up DUMPSTATION_SECRET_KEY separately. It encrypts stored database passwords, storage keys, webhooks and TOTP secrets. Losing it makes them unrecoverable; changing it breaks decryption.

  3. Start it
    terminal
    docker compose up -d
docker compose logs -f dumpstation   # wait for "Auto-migration completed successfully"
  4. Sign in

    Open http://localhost:8080 (or your domain), enter admin and request a code. Without DISCORD_WEBHOOK_URL the code is written to the server log:

    terminal
    docker compose logs dumpstation | grep "OTP not sent"
  5. Turn on two-factor authentication

    Under Settings → Security, before you expose the server. Then continue with your first backup.

The configurator on the home page generates a ready .env with fresh secrets in your browser.

Reverse proxy & TLS

Put one hostname in front of the server for every path (/, /api/, /agent/, /config.js) and set PUBLIC_URL to it. Agents long-poll and may stream large artifacts, so /agent/ needs long timeouts and no body limit.

backups.example.com {
    reverse_proxy dumpstation:8080 {
        flush_interval -1
        transport http {
            read_timeout 6h
            write_timeout 6h
        }
    }
}
server {
    listen 443 ssl http2;
    server_name backups.example.com;
    # ssl_certificate ...; ssl_certificate_key ...;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 120s;
    }

    # Agent protocol: long-polls and streamed artifact transfers.
    location /agent/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        client_max_body_size 0;
        proxy_request_buffering off;
        proxy_buffering off;
        proxy_http_version 1.1;
        proxy_read_timeout 6h;
        proxy_send_timeout 6h;
    }
}
# traefik.yml — raise entrypoint timeouts (v3 defaults readTimeout to 60s)
entryPoints:
  websecure:
    address: ":443"
    transport:
      respondingTimeouts:
        readTimeout: 0
        writeTimeout: 0
# Do not attach a buffering middleware with a body limit to /agent/.

Set TRUST_PROXY_HEADERS=true when the proxy is yours, so login rate limits and the activity log see real client IPs.

Behind Cloudflare or another CDN? Proxied plans cap request bodies (100 MB on free) and hold requests for about 100 s. Long-polls fit; proxied transfers of large backups don't. Let agents upload directly to storage (auto / direct) or expose a hostname for agents that bypasses the CDN.

Sign-in & security

One-time codes

Users sign in with a username and a 6-digit code. Codes go to DISCORD_WEBHOOK_URL when set, otherwise to the server log. They expire after OTP_EXPIRATION_MINUTES.

GitHub

  1. Create an OAuth app at github.com/settings/developers.
  2. Set its callback URL to https://backups.example.com/api/v1/auth/github/callback.
  3. Set GITHUB_CLIENT_ID, GITHUB_CLIENT_SECRET, GITHUB_ALLOWED_LOGIN and GITHUB_REDIRECT_URL. Only that one account can sign in; it becomes an administrator on first sign-in.

Two-factor authentication

TOTP from Settings → Security, with recovery codes. Once enabled it is enforced for GitHub sign-ins too.

Turnstile

Set TURNSTILE_ENABLED=true and both keys to put a Cloudflare Turnstile challenge on code requests.

What's protected, and how

  • Secrets at rest (database passwords, storage keys, webhook URLs, TOTP secrets, Explorer credentials) are encrypted with AES-256-GCM under DUMPSTATION_SECRET_KEY.
  • Every resource has an owner; administrators can see all and manage roles. The demo account is read-only.
  • Downloading an artifact needs a code sent to one of your notification channels, then gives a presigned URL valid for 5 minutes.
  • The activity log records logins, configuration changes, backups, restores and agent events for 60 days.

Your first backup

  1. Add storage

    Storage → Add storage. Pick the provider, bucket, endpoint and keys, then Test: it writes, reads and deletes a probe object under .dumpstation/ and tells you which step failed. The first storage becomes the default.

  2. Add a database

    Databases → Add database (or ⌘K → "Add database"). Choose Direct if the server can reach it, Agent if not. Test connection checks reachability, authentication, the server version and that a compatible pg_dump exists.

  3. Pick a schedule and retention

    A preset or cron expression, an IANA time zone, and keep-last-N or keep-N-days. See schedules & retention.

  4. Back up now

    Press Back up now and follow the job: queued → connecting → dumping → uploading → verifying → retention. Every stage is logged.

The backup role must be able to read everything in the database: the owner, or pg_read_all_data on PostgreSQL 14+.

The access key needs only object-level actions; no ListBucket, no bucket CORS:

iam-policy.json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject", "s3:AbortMultipartUpload"],
    "Resource": "arn:aws:s3:::my-dumpstation-backups/*"
  }]
}

Each backup remembers the storage it was written to. Changing a database's storage only affects new backups; older ones are restored from and deleted in their original bucket. Consider a lifecycle rule that aborts incomplete multipart uploads after a day, and object lock if you need protection against deletion.

Schedules & retention

Schedules are cron expressions or presets (hourly, every N hours, daily, weekly, monthly) evaluated in the database's IANA time zone, with a preview of the next runs. Runs missed while the server was down are detected and reported, and can notify you.

RetentionRangeKeeps
count1–10,000The N newest successful backups.
days1–3,650Successful backups started within the last N days.

The newest successful backup is never deleted, whatever the policy. A broken schedule can't leave you with nothing.

Retention runs after every successful backup. Failed and cancelled backups aren't counted; purge them from the Backups page. Pause stops scheduled runs while manual backups still work.

Restore

Open a successful backup and choose Restore. The wizard has three steps: target, options, confirmation.

TargetRuns onNotes
Original databaseits executorRestores into the source; typed confirmation.
Another configured databasethat database's executorGreat for staging copies; typed confirmation.
Custom targetthe server or an agent you pickEnter connection details or pick an agent's local connection.
  • --clean runs pg_restore --clean --if-exists. Without it, existing objects cause errors.
  • Restores always use --no-owner --no-privileges. The target database must already exist.
  • The artifact's SHA-256 is checked against the value recorded at backup time before anything is restored.
  • Through an agent, both Allow restores on the server and DUMPSTATION_ALLOW_RESTORE=true on the agent are required.
  • Restores are never retried automatically.

Prefer the command line? Download the artifact and run:

terminal
pg_restore --no-owner -d mydb backup.dump

Notifications

Notifications → Add channel. A channel holds a Discord webhook, a Telegram bot token and chat ID, or both; Test sends a message. Assign it to databases to receive:

  • backup success (size, duration) and failure (with the error code);
  • restore success and failure;
  • missed scheduled runs;
  • the database's agent going offline or coming back.

For Telegram, create a bot with @BotFather; get a chat ID from @userinfobot or by adding the bot to a group. The server-wide DISCORD_WEBHOOK_URL is separate: it only receives sign-in codes and start/stop notices.

How agents work

An agent is a small worker that backs up (and optionally restores) databases the server can't reach. It runs inside the private network, makes outbound HTTPS requests only, and executes only backup, restore and test_connection jobs.

It needsWhy
Outbound HTTPS to PUBLIC_URLControl traffic and, in proxy mode, artifact transfers.
Network access to the databasespg_dump / pg_restore connect from the agent host.
Outbound HTTPS to storage (optional)Direct uploads via presigned URLs; otherwise uploads go through the server.
A persistent state directoryHolds the credential issued at enrollment.
Temp disk ≥ your largest compressed dumpDumps are written to disk before upload.

Registration

  1. Backup Agents → Add agent: name, restore permission (off by default), token lifetime (15 min, 1 h or 24 h).
  2. Copy the single-use dse_… enrollment token and one of the ready-made snippets.
  3. Start the agent. It enrolls, stores its credential, and the wizard flips to online.
  4. Databases → Add database → Agent, pick the agent and one of its connections.

Install an agent

The image ghcr.io/monzim/dumpstation-agent runs as UID 10001, keeps state in /var/lib/dumpstation-agent and bundles PostgreSQL client tools 12–18.

The Kubernetes manifest is a single-replica StatefulSet with a small PVC for state, a read-only root filesystem, all capabilities dropped and an exec liveness probe. No Service or Ingress is needed. Keep replicas: 1; for more capacity, deploy another agent.

Leaving DUMPSTATION_ENROLLMENT_TOKEN set after enrollment is harmless: the agent only re-enrolls when the value changes.

Connections

Agents back up named connections defined on the agent host. The server only sees the name; passwords never leave the host. Define them as env vars or in a YAML file.

# name "orders": lower-cased, _ becomes -
DUMPSTATION_CONN_ORDERS=postgres://backup_user@orders-db.internal:5432/orders?sslmode=require
DUMPSTATION_CONN_ORDERS_PASSWORD_FILE=/run/secrets/orders_password
# /etc/dumpstation-agent/connections.yaml (or DUMPSTATION_CONNECTIONS_FILE)
connections:
  orders:
    url: postgres://backup_user@orders-db.internal:5432/orders?sslmode=require
    password_file: /run/secrets/orders_password
  analytics:
    host: 10.20.0.15
    port: 5432
    database: analytics
    user: backup
    password_env: ANALYTICS_DB_PASSWORD
    sslmode: prefer

Check what an agent sees with docker exec dumpstation-agent dumpstation-agent connections. Restart the agent after changing connections.

Operations & sizing

  • Health: GET /api/v1/health (unauthenticated, used by the image's HEALTHCHECK). System Health in the UI shows version, uptime, DB latency, client tools and enabled sign-in methods.
  • Logs: docker compose logs -f dumpstation, plus an execution log per job in the UI.
  • Back up the metadata database (configs/manage.sh backup) and store DUMPSTATION_SECRET_KEY separately. Artifacts in storage are plain pg_dump files and stay restorable without DumpStation.
  • Graceful shutdown: on SIGTERM the server stops the scheduler, drains HTTP for 30 s, then cancels running direct jobs (marked interrupted). Agent jobs are unaffected.
  • Upgrades: pull and recreate; migrations run on start. Pin DUMPSTATION_VERSION in production.

CPU1–2 vCPUCompression for direct backups.
Memory256–512 MiB+ ~64 MiB per concurrent upload.
Temp disklargest dump × concurrencyOnly for direct backups and restores.

Upgrading from v1

v2 serves the UI from the server itself, so the separate web service goes away. Existing databases become direct databases, and secrets keep working.

  1. Stop v1

    docker compose down. Volumes are kept. Back up the metadata database first.

  2. Swap the Compose file

    Use the v2 configs/compose.yml, or delete the web service and map the server to 8080. Keep your PostgreSQL image major version.

  3. Update .env

    Set DUMPSTATION_SECRET_KEY (your existing key), PUBLIC_URL, APP_ENV=production. Drop VITE_*, WEB_PORT, BACKEND_PORT.

  4. Point the proxy at one upstream

    Every path to port 8080. GitHub users: update the OAuth callback to https://<host>/api/v1/auth/github/callback.

  5. Start and verify

    docker compose pull && docker compose up -d, wait for "Auto-migration completed successfully", test each storage and run one manual backup.

Troubleshooting

Every failed job carries a typed error code, shared by the server, agents and UI.

CodeMeaningWhat to do
auth_failedWrong password, no password, role missing, or pg_hba.conf rejected the connection.Check credentials (on the agent for local connections) and add a pg_hba.conf entry for the executor's IP.
host_unreachableDNS failure, refused, no route, or 15 s connect timeout.Check host/port from the executor's network. A private host usually means: use an agent.
database_not_foundThe database name doesn't exist.Fix the name; for restores create the target first.
permission_deniedThe role can't read some objects (or must own them to restore).Use the owner or pg_read_all_data; for restores, --clean with an owner.
version_mismatchNo installed pg_dump new enough, or an archive from a newer pg_dump.Use the official images, or add a newer client to PG_BIN_DIRS.
ssl_errorSSL negotiation or certificate verification failed.Check sslmode; use disable for local containers without SSL.
insufficient_diskTemp space below the minimum, or disk full.Grow the temp volume, lower concurrency.
timeoutRan longer than BACKUP_TIMEOUT_MINUTES.Raise the limit; check locks and storage speed.
cancelledCancelled by a user, or the lease was lost during upload.Re-run if needed.
tool_missingNo PostgreSQL client tools on the executor.Use the official image or install postgresql-client.
upload_failedUpload to storage failed.Run the storage Test; for agents try DUMPSTATION_TRANSFER_MODE=proxy.
download_failedCouldn't fetch the artifact for a restore.Check the object exists and is reachable; try proxy mode.
verification_failedObject missing or size differs, or checksum mismatch on restore.Re-run the backup; for restores pick another backup and check bucket integrity.
storage_errorStorage config missing or invalid, or presigning failed.Check endpoint, region and keys; run Test.
agent_unavailableAgent revoked, disabled, or didn't pick the job up in time.Start or enable the agent; re-enroll a revoked one.
agent_lostThe agent stopped reporting progress.Check agent logs for crashes, OOM kills or network loss.
configuration_errorInvalid fields, unknown connection name, restores disabled, or host blocked by DIRECT_ALLOWED_CIDRS.Read the message; check dumpstation-agent connections.
restore_failedpg_restore reported errors.Read the output tail; use --clean or an empty database; create missing roles/extensions.
dump_failedpg_dump failed for another reason or produced an empty file.Read the output tail (locks, catalog issues).
interruptedThe server restarted during a direct job.Re-run; use agents for jobs that must survive restarts.
unknownUnclassified.Read the message and the server/agent logs.

Common problems

  • Agent won't enroll: the token is single-use and expires; create a new one. Check the agent can reach PUBLIC_URL over HTTPS.
  • Agent shows offline: it hasn't sent a heartbeat recently. Check its logs and outbound network; dumpstation-agent healthcheck prints the reason.
  • Backups stuck in waiting_for_agent: the agent is offline or busy; jobs fail after AGENT_JOB_QUEUE_TTL_MINUTES.
  • No sign-in code: without a Discord webhook, look for "OTP not sent" in the server log.

Build from source

Go 1.25 and Node with pnpm. The server serves the built UI from WEB_DIR.

terminal
git clone https://github.com/monzim/DumpStation.git && cd DumpStation
cd web && pnpm install && pnpm build && cd ..
cd server && go build -o dumpstation ./cmd/server
WEB_DIR=../web/dist ./dumpstation             # plus the DB_* and secret variables

CGO_ENABLED=0 go build -o dumpstation-agent ./cmd/agent   # the agent
