How it works

Two ways to reach a database. One job lifecycle.

The server decides what runs and where. It runs pg_dump itself when it can reach the database, and hands the job to an agent inside the network when it can't. Same history, retention, verification and alerts either way.

Agent: for databases the server can't see

Private subnets, other clouds, a box behind NAT. Run one small container next to the database and it does the work there.

  • Outbound HTTPS only. Enroll, heartbeat and long-poll for jobs. No published ports, no VPN, no firewall rules.
  • Credentials stay on the host. Connections are named locally; the server only ever sees the name.
  • Whitelisted job kinds. Backup, restore (opt-in on both sides) and connection tests. Nothing else.
  • Direct-to-bucket transfers with presigned URLs, or streamed through the server when the bucket is unreachable.

Direct: zero extra moving parts

If the server can reach the database, that's all you need. Managed Postgres, a VPS, the container next door.

  • Right client, every time. pg_dump 12 through 18 are bundled; the version is matched to each server.
  • Network guardrails. DIRECT_ALLOWED_CIDRS pins which hosts the server may connect to.
  • Verified before success. SHA-256 while dumping, object size checked in storage after upload.
  • Concurrency control. BACKUP_CONCURRENCY caps parallel dumps and restores; the rest queue.

Features

Everything between pg_dump and a good night's sleep.

Scheduling, storage, verification, retention, restore and alerting in one place, with sensible defaults and nothing to babysit. Try the pieces below.

Schedules

Cron or presets, in the database's own time zone.

Every database gets an IANA time zone and a preview of the next runs. Missed runs, say while the server was down, are detected and reported.

    Storage

    Any S3-compatible bucket. Pinned per backup.

    AWS S3, Cloudflare R2, MinIO, Backblaze B2, Wasabi, Spaces, Garage, Ceph. Each backup remembers where it was written, so moving a database to new storage never orphans its history. Built-in test writes, reads and deletes a probe object and tells you which step failed. Needs only four object-level permissions; no CORS, no ListBucket.

    Deploy

    From zero to first backup in three steps.

    Enter your domain and the commands fill themselves in. Secrets are generated in your browser and never leave it.

    1. Configure the server

      Copy the Compose bundle and drop in a generated .env.

    2. Start it and sign in

      Bring the stack up. Without a Discord webhook, your sign-in code is in the log.

    3. Add an agent (optional)

      For a private database: one container, one enrollment token, outbound only.

    Then in the UI: add storage, add a database, press Back up now. TLS, reverse proxies and Kubernetes are in the docs.

    Security

    It holds the keys to your data. It's built like it.

    Encrypted at rest

    Database passwords, storage keys, webhooks and TOTP secrets are sealed with AES-256-GCM under your DUMPSTATION_SECRET_KEY.

    Passwordless sign-in + 2FA

    One-time codes, optional GitHub OAuth for a single allowed account, TOTP enforced on both, and Cloudflare Turnstile if you want it.

    Roles & tenant isolation

    Every resource has an owner. Admins see everything and manage roles; an optional read-only demo account is safe to share.

    Least-privilege agents

    Single-use enrollment tokens, revocable credentials, restores disabled unless enabled on the agent and in the server.

    Activity log

    Logins, configuration changes, backups, restores and agent events, kept for 60 days.

    Downloads behind a code

    Pulling a dump to your laptop needs a fresh one-time code and gets a short-lived presigned URL.

    FAQ

    Questions, answered.

    Is it free?

    Yes. DumpStation is MIT licensed and fully self-hosted. You pay only for the machine it runs on and your object storage.

    What does a backup contain?

    A pg_dump custom-format archive (--format=custom) of one database: schema and data, compressed, restorable with pg_restore with or without DumpStation. Roles and other cluster-wide objects are not included.

    Do agents need a VPN or open ports?

    No. Agents make outbound HTTPS requests to your server's PUBLIC_URL and nothing else needs to reach them. Uploads go straight to the bucket with presigned URLs when the agent can reach it, or stream through the server when it can't.

    Where do database passwords live?

    For direct databases, encrypted in DumpStation's metadata database. For agent databases, only on the agent host, as an env var, a password file or a connections YAML. The server only sees a connection name.

    Which PostgreSQL versions are supported?

    Servers from 12 to 18. The images bundle every client version and pick the right pg_dump for each server, so dumping a newer server never fails with a version mismatch.

    What happens if the DumpStation server dies?

    Your artifacts are plain pg_dump files in your bucket, restorable by hand. Back up the metadata database too (configs/manage.sh backup) and keep the secret key somewhere separate. Agent jobs survive server restarts; direct jobs are marked interrupted.

    Can I upgrade from v1?

    Yes. Pull the v2 image and recreate the container; migrations run on start and existing secrets keep working. The upgrade guide covers the details and how to roll back.
